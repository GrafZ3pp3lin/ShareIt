# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

ShareIt frontend: a SolidJS SPA for uploading and sharing content packages (files/text), with optional OIDC login (guests get an auto-generated ID) and optional client-side encryption of pasted text and files (one passphrase per package).

## Commands

```bash
pnpm dev              # vite dev server on http://localhost:3001 (plain http; localhost is a secure context, so crypto.subtle works)
pnpm build             # tsc -b && vite build -> dist/
pnpm test              # vitest (watch mode)
pnpm test:ui           # vitest with UI
pnpm lint              # oxlint
pnpm lint:fix          # oxlint --fix
pnpm format            # oxfmt (write)
pnpm format:check      # oxfmt (check only)
pnpm knip              # unused exports/deps/files
pnpm generate:open-api # regenerate src/client from a *running* backend at http://localhost:5155/openapi/v1.json
```

Run a single test file: `npx vitest run src/shared/crypto/crypto.test.ts`.

oxlint runs with type-aware linting enabled (`.oxlintrc.json` → `options.typeAware`, powered by `oxlint-tsgolint`) plus the `typescript` plugin. Type-aware rules like `no-floating-promises` and `no-misused-promises` need that package — don't remove it from devDependencies.
Run a single project: `npx vitest run --project unit` or `--project components`.

There are two Vitest projects (`vite.config.ts`):

- `unit`: `*.test.ts` / `*.spec.ts` files, `environment: 'node'` — pure logic (crypto, error mapping).
- `components`: `*.test.tsx` / `*.spec.tsx` files, `environment: 'happy-dom'`, setup file `src/tests/vitest-setup.ts` — Solid component tests via `@solidjs/testing-library`, plus anything needing a DOM (`XMLHttpRequest`, `localStorage`).

Tests are co-located next to the source file, not in a `__tests__` dir.

`generate:open-api` requires the backend to be running locally and serving its OpenAPI spec at `http://localhost:5155/openapi/v1.json` (see `orval.config.ts`) — it is not run from a checked-in spec file.

## Architecture

### Routing and app bootstrap

Routing is code-based via `@solidjs/router` (`createRouter`), not file-based.

- `src/index.tsx` → `src/app.tsx` → `src/app/providers.tsx` (`AppProviders`), which nests, in order: `ThemeProvider` → `I18nProvider` → `AuthProvider` → `Router` (the `createRouter` instance is the provider component).
- `src/app/router.tsx` creates the router from `routeTree` (`src/shared/routes/route-tree.tsx`).
- `src/shared/routes/route-tree.tsx` is the **single wiring point**: it declares the route tree (`defineRoutes`) — a `path: '/'` root route whose component is `AppLayout`, with children for `/`, `/auth/callback`, `/s/:packageId`, `/account`, importing each page component from the corresponding `src/features/*/pages/*`. Features never self-register — this file is where a new route must be added.
- `src/app/layout.tsx` (`AppLayout`) is the root route's component: header/nav (conditioned on `useAuth()` state) + `{props.children}` + footer. Links are plain `<a href>` elements; the router styles active state via `data-active` (see the `nav-tab` utility in `src/index.css`).

### Feature module convention

`src/features/<name>/`:

- `pages/<name>-page.tsx` — the route-level component, one per entry in the route tree.
- `components/` — presentational components local to that feature.
- Feature-local state/context sits directly under the feature root, e.g. `src/features/auth/auth-context.tsx` next to `pages/`.

Features consume cross-cutting concerns from `src/shared/*` (`api`, `auth`, `crypto`, `config`) and `src/i18n`; they don't reach into each other.

### Generated API client + wrapper

`src/client/**` is entirely generated by Orval (`orval.config.ts`, `npm run generate:open-api`) — never edit it by hand. Orval calls go through the mutator in `src/shared/api/fetch-client.ts` (`customFetch`), which adds the runtime base URL and identity headers and returns the generated `{ data, status, headers }` shape. `src/client/**` is excluded from oxlint (`.oxlintrc.json`); app wrappers in `src/shared/api/` map that result shape to `ApiResult` with type guards (no assertions). Orval renders int64 fields as `number | string` — the `getUploadLimits()` wrapper's `isUploadLimits` guard narrows them to plain numbers.

The app never calls generated SDK functions directly except through `src/shared/api/`:

- `client.ts` — `configureApiClient()` sets the real `baseUrl` from `getRuntimeConfig().apiBaseUrl` (overriding the generated client's hardcoded dev default) and registers a request interceptor that attaches either an OIDC `Authorization` bearer token (`getAuthToken()`) or, if not authenticated, a persisted guest ID header (`X-Guest-ID`, from `localStorage` key `shareit-guest-id`) — i.e. uploads work anonymously. `getAuthHeaders()` exposes the same identity headers for the XHR-based uploader.
- `content.ts` — thin app-level wrappers around generated SDK calls (`createContentPackage`, `getPackageDetails`, `downloadContent`), the upload-limits query (`getUploadLimits`), and `uploadFile()` — an XHR-based single-file uploader with real progress reporting and `AbortSignal` cancellation.
- `error-message.ts` — `getErrorMessage()` normalizes error shapes (string, `Error`, RFC7807 `ProblemDetails`, generic `{message}`) into a display string.

### Upload flow (two-step hybrid)

`upload-page.tsx` submits in two steps: (1) `POST /package` creates the package with metadata and the encrypted text inline (`Texts`), then (2) each file is encrypted client-side and uploaded individually (`POST /package/{id}/upload`) with per-file progress and cancel support. Per-file size limits come from the backend `GET /package/limits` endpoint (anonymous vs authenticated), applied client-side before upload and enforced server-side.

### Auth (OIDC)

`oidc-client-ts`, authorization-code flow (no client secret, SPA).

- `src/shared/auth/oidc.ts`: `getOidcSettings()` returns `null` if `authAuthority`/`authClientId` are missing from runtime config — this is how auth is fully optional/disabled per-environment. `getUserManager()` memoizes a singleton `UserManager` (or `null`).
- `src/features/auth/auth-context.tsx`: `AuthProvider`/`useAuth()` wraps the manager with Solid signals (`user`, `isLoading`, `isAuthenticated`, `isEnabled`) and exposes `login()`, `logout()`, `handleCallback()`.
- `src/features/auth/pages/auth-callback-page.tsx` handles the `/auth/callback` route: calls `handleCallback()` then navigates to `/`.
- Client ID/authority/scope/redirect URIs are never hardcoded — always read through `getRuntimeConfig()`.

### Runtime configuration (build once, configure per-deploy)

The app is a static SPA that must be reconfigured without rebuilding per environment (dev/stage/prod), documented in `docs/runtime-config.md`.

- `index.html` loads `/env.js` (a plain script, before the module bundle) which sets `window.env`.
- `src/shared/config/runtime-config.ts`: `getRuntimeConfig()` resolves each setting as `window.env` value → `import.meta.env.VITE_*` fallback → built-in default, computed once at import time.
- `public/env.js` — dev default (`ApiBaseUrl: http://localhost:5155`, auth fields empty → OIDC disabled locally by default).
- `docker/env.template.js` + `docker/40-env.sh`: at container start, `40-env.sh` runs in nginx's `/docker-entrypoint.d/` and `envsubst`s real container env vars (`API_BASE_URL`, `AUTH_AUTHORITY`, `AUTH_CLIENT_ID`, `AUTH_REDIRECT_URI`, `AUTH_POST_LOGOUT_REDIRECT_URI`, `AUTH_SCOPE`) into `env.template.js` → `dist/env.js`. This is how one Docker image serves multiple environments.
- Keep secrets out of `env.js`/`env.template.js` — it's public in the browser.

### Client-side crypto

`src/shared/crypto/` implements optional AES-GCM encryption for **both pasted text and files** (one passphrase per package, generated client-side and shown once).

- `crypto.ts`: `generatePassphrase()` (random, shown once to the user), `deriveKey()` (PBKDF2-SHA256, 150k iterations), `encryptText()`/`decryptText()` for text, and `encryptFile()`/`decryptFile()` for files.
- `envelope.ts`: `EncryptedTextEnvelope` JSON shape (`{v, alg, iter, salt, iv, ct}`) and `parseEncryptedTextEnvelope()` — the encrypted envelope's JSON serialization is literally what gets uploaded as "text content", and its presence/shape is how `share-page.tsx` detects an item needs a passphrase to decrypt.
- Files use a **binary** envelope (avoids the ~33% base64 JSON bloat): magic `SIE1` + salt + IV + PBKDF2 iterations + AES-GCM ciphertext. Encrypted files are uploaded with MIME type `application/x-shareit-encrypted` (`ENCRYPTED_FILE_MIME_TYPE`), which is how the share page detects a file needs decryption; the magic header is also sniffed after download.

### i18n

`@solid-primitives/i18n`, `src/i18n/i18n.tsx` (`I18nProvider`/`useI18n()`) + `src/i18n/en.ts` (only locale currently). Translation dict is namespaced by feature (`app`, `upload`, `share`, `auth`, `account`), mirroring `src/features/*`. `t('some.key', { placeholder })` supports `{{ }}` interpolation. No locale-switch UI is wired yet even though the store supports `setLocale`.

## Tooling conventions

- Relative imports must include explicit file extensions (`import/extensions` oxlint rule), e.g. `from '../../client/client.gen.ts'`.
- oxfmt: single quotes, semicolons, no trailing commas, 120 print width, `arrowParens: always`.
- `src/client/**` is intentionally excluded from lint and from knip's unused-export checks — don't try to "clean up" the generated client.
